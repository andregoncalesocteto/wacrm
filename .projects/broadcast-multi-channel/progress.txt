- **Replay DB network collision when the dev stack is already up**: `docker-compose.yml` declares `wacrm-net` as a
  fixed-name network (`networks.wacrm-net.name: wacrm-net`), shared literally (not project-scoped) between the
  default `wacrm` project and any `-p wacrm-replay` run — both `db` containers register the SAME network alias
  `db`, so anything resolving hostname `db` while both stacks are up gets Docker's DNS round-robin between the
  two Postgres instances (symptom: `migrate` mid-run suddenly sees "relation does not exist" or a duplicate-key
  error on an already-applied migration name — it silently bounced between the two DBs). The `migrate.sh` script
  and the `migrate` compose service always use `PGHOST: db` from the compose file's `environment:`, so you can't
  avoid this by just being careful. Fix: override PGHOST to the replay container's own unique alias when running
  migrate: `$R run --rm -T -e PGHOST=wacrm-replay-db-1 migrate` (the container's own alias is always
  `<project>-<service>-1`, confirm with `docker inspect wacrm-replay-db-1 --format '{{json
  .NetworkSettings.Networks}}'`). `$R exec -T db ...` for `auth`/`rest`/`storage`/`verify-schema` is fine as-is
  (those are project-scoped `docker compose exec`, which targets the container by compose project, not DNS). Every
  migration file's DDL is idempotent (`IF NOT EXISTS`/`DROP ... IF EXISTS`) and `migrate.sh` runs one transaction
  per file, so a collision aborts cleanly with no partial state on either DB — but still confirm the dev DB wasn't
  left inconsistent (`SELECT count(*), count(distinct name) FROM public.wacrm_migrations` should match, no
  duplicates) before trusting it after a collision. Future migration stories (US-002) should use this
  `-e PGHOST=wacrm-replay-db-1` override every time the main stack might be up.

- Scope decision, worth flagging explicitly: the AC asks createBroadcast to persist template OR free-message

  free-message content through the only live route today would let a caller create a broadcast that
  `deliverBroadcast` can't send correctly once `provider.capabilities.templates` is true (a benign "unsupported"
  failure for a non-template channel, but a REAL broken-template-send risk for a WhatsApp connection, since
  `plan.templateName` would be `''`). Keeping the route template-only until US-005 lands avoids that risk
  entirely while still satisfying the AC's literal requirement at the function level. Whoever picks up US-005
  (or a later story that wires the dashboard route through this core) should revisit whether the route should
  gain `message_text`/`message_media_url` at that point.

  change). For `capabilities.initiate !== 'template'`, the target is resolved via `provider.resolveTarget(identities)`
  — the exact method `lib/channels/send.ts`'s `sendOutbound` already uses for a regular conversation send —
  where `identities` comes from a new local helper `loadRecipientIdentities(db, contactId)` that reads
  `contact_identities` filtered by `contact_id` (no whatsapp_cloud/`contacts.phone` fallback: unnecessary, since
  no built-in provider with `capabilities.initiate !== 'template'` resolves off `contacts.phone`). If
  `resolveTarget` returns null (contact has no identity for this channel), the recipient is stamped `failed` with
  `error_message: 'No reachable address on this channel'` — same best-effort-per-recipient shape as any other send
  failure, never aborting the rest of the loop.
  This required threading `contactId` through the shared recipient shape both plan-builders produce: added
  `contactId: string` to `PlannedRecipient` (broadcast-core.ts), populated from the RPC's `contact_id` column in
  `createBroadcast`, and from `broadcast_recipients.contact_id` (added to the `select`) in
  `planBroadcastResume` (broadcast-resume.ts) — confirming the AC's "broadcast-resume.ts herda a mesma resolução"
  literally, not by assumption: both plan-builders now feed the exact same `deliverBroadcast` target-resolution
  code path.
- `broadcast-resume.ts`'s own phone-based "unsendable" pre-filter (previously applied unconditionally to every
  channel, marking any row without a valid E.164 `contacts.phone` as `failed` up front) was the actual live
  instance of the AC's "eligible contact with phone='' silently dropped" bug for a resumed campaign — a phone-less
  Telegram contact hitting a resume pass would have been marked failed with "No valid phone number on contact"
  before ever reaching `deliverBroadcast`. Fixed by resolving the connection (and `provider.capabilities.initiate`)
  BEFORE building the sendable/unsendable split, and only running the phone pre-filter when `isTemplatePath` is
  true; for a non-template channel every in-scope row is now `sendable` and `deliverBroadcast` resolves (or fails)
  each one individually via `contact_identities`, exactly like a fresh send. This moved the connection-resolution

  behavior change for the template path (same lookups, same error codes, same order of `not_found`/

- **Learnings for future iterations:**
  - `loadRecipientIdentities(db, contactId)` (broadcast-core.ts, local/unexported) is now the broadcast-specific
    counterpart of `lib/channels/send.ts`'s private `loadIdentities` — narrower on purpose (no `contacts.phone`
    fallback, since it's only ever called on the non-template path). If a future story needs the SAME
    identity-based resolution outside `deliverBroadcast`, consider promoting one shared helper instead of a third
    copy.
  - `PlannedRecipient.contactId` is now load-bearing for both plan-builders — any future third builder of a
    `BroadcastPlan` (there are only two today: `createBroadcast` and `planBroadcastResume`) MUST populate it, or
    every non-template recipient it plans will fail with "No reachable address on this channel".
  - The connection-resolve-before-recipient-filter reorder in `planBroadcastResume` is a good pattern for "this
    decision depends on the channel" logic in general — resolve the connection/provider first, branch the
    recipient-shaping logic on `provider.capabilities` second. US-013's route-level validation (`connection_id`
    required, content exclusivity, `connection_channel_mismatch`) will likely want the same ordering.
  - Confirmed by reading (not assuming): no built-in provider (`whatsapp-cloud`, `telegram`) with
    `capabilities.initiate !== 'template'` ever resolves a target from `contacts.phone` — so
    `loadRecipientIdentities` correctly has zero phone fallback. If a future non-template provider DID want a
    phone fallback, it would need to be added there explicitly (or via a whatsapp-cloud-style identities
    fallback), not assumed to already work.
