- **Replay DB network collision when the dev stack is already up**: `docker-compose.yml` declares `wacrm-net` as a
  fixed-name network (`networks.wacrm-net.name: wacrm-net`), shared literally (not project-scoped) between the
  default `wacrm` project and any `-p wacrm-replay` run — both `db` containers register the SAME network alias
  `db`, so anything resolving hostname `db` while both stacks are up gets Docker's DNS round-robin between the
  two Postgres instances (symptom: `migrate` mid-run suddenly sees "relation does not exist" or a duplicate-key
  error on an already-applied migration name — it silently bounced between the two DBs). The `migrate.sh` script
  and the `migrate` compose service always use `PGHOST: db` from the compose file's `environment:`, so you can't
  avoid this by just being careful. Fix: override PGHOST to the replay container's own unique alias when running
  migrate: `$R run --rm -T -e PGHOST=wacrm-replay-db-1 migrate` (the container's own alias is always
  `<project>-<service>-1`, confirm with `docker inspect wacrm-replay-db-1 --format '{{json
  .NetworkSettings.Networks}}'`). `$R exec -T db ...` for `auth`/`rest`/`storage`/`verify-schema` is fine as-is
  (those are project-scoped `docker compose exec`, which targets the container by compose project, not DNS). Every
  migration file's DDL is idempotent (`IF NOT EXISTS`/`DROP ... IF EXISTS`) and `migrate.sh` runs one transaction
  per file, so a collision aborts cleanly with no partial state on either DB — but still confirm the dev DB wasn't
  left inconsistent (`SELECT count(*), count(distinct name) FROM public.wacrm_migrations` should match, no
  duplicates) before trusting it after a collision. Future migration stories (US-002) should use this
  `-e PGHOST=wacrm-replay-db-1` override every time the main stack might be up.

  content, so the function fully supports both shapes (tested directly). BUT `POST /api/v1/broadcasts`

  free-message content through the only live route today would let a caller create a broadcast that
  `deliverBroadcast` can't send correctly once `provider.capabilities.templates` is true (a benign "unsupported"
  failure for a non-template channel, but a REAL broken-template-send risk for a WhatsApp connection, since
  `plan.templateName` would be `''`). Keeping the route template-only until US-005 lands avoids that risk
  entirely while still satisfying the AC's literal requirement at the function level. Whoever picks up US-005
  (or a later story that wires the dashboard route through this core) should revisit whether the route should
  gain `message_text`/`message_media_url` at that point.

    replay's OWN db never got `storage.buckets` etc., so `migrate` failed at `008_profile_avatars_storage.sql`
    with "relation storage.buckets does not exist", and `verify-schema.sql`'s storage check would have failed
    too). Fix used this session (not committed, repo-external): a throwaway docker-compose override file (in the
    scratchpad, `-f <override>`) pinning `DATABASE_URL`/`GOTRUE_DB_DATABASE_URL`/`PGRST_DB_URI` to
    `wacrm-replay-db-1` for `storage`/`auth`/`rest`, then `up -d --force-recreate --wait db auth storage rest`
    before running `migrate`. No repo file was changed for this (transient, per-session workaround) — a FUTURE
    story that touches `docker-compose.supabase.yml` might consider giving `db` a project-scoped alias instead of
    the fixed network-wide one, which is the actual root cause. No evidence of any write reaching the dev auth/
    storage schemas beyond a no-op schema-migration check (no signups/uploads were sent to the replay stack), so
    dev data integrity was verified intact afterwards, but this is worth knowing before trusting a replay
    `up -d --wait db auth storage` at face value while the dev stack is up.
  - `getConnectionById(id, db)` + `conn.account_id === accountId` (mirroring `POST /api/v1/messages`'
    `pickConnection`) is the established "generic connection lookup, no channel_type filter" idiom in this
    codebase now — reuse it verbatim for US-006/US-008 rather than reinventing.
  - The `broadcasts_content_exclusive_check` CHECK from migration 052 is a strict XOR
    (`(template_name IS NOT NULL) <> (message_text IS NOT NULL OR message_media_url IS NOT NULL)`) — mirroring it
    in application code as `hasTemplate === hasMessage -> reject` (rather than two separate "missing"/"both"
    checks) is the shortest correct implementation and is easy to eyeball against the SQL.
