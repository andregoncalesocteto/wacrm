- **Replay DB network collision when the dev stack is already up**: `docker-compose.yml` declares `wacrm-net` as a
  fixed-name network (`networks.wacrm-net.name: wacrm-net`), shared literally (not project-scoped) between the
  default `wacrm` project and any `-p wacrm-replay` run — both `db` containers register the SAME network alias
  `db`, so anything resolving hostname `db` while both stacks are up gets Docker's DNS round-robin between the
  two Postgres instances (symptom: `migrate` mid-run suddenly sees "relation does not exist" or a duplicate-key
  error on an already-applied migration name — it silently bounced between the two DBs). The `migrate.sh` script
  and the `migrate` compose service always use `PGHOST: db` from the compose file's `environment:`, so you can't
  avoid this by just being careful. Fix: override PGHOST to the replay container's own unique alias when running
  migrate: `$R run --rm -T -e PGHOST=wacrm-replay-db-1 migrate` (the container's own alias is always
  `<project>-<service>-1`, confirm with `docker inspect wacrm-replay-db-1 --format '{{json
  .NetworkSettings.Networks}}'`). `$R exec -T db ...` for `auth`/`rest`/`storage`/`verify-schema` is fine as-is
  (those are project-scoped `docker compose exec`, which targets the container by compose project, not DNS). Every
  migration file's DDL is idempotent (`IF NOT EXISTS`/`DROP ... IF EXISTS`) and `migrate.sh` runs one transaction
  per file, so a collision aborts cleanly with no partial state on either DB — but still confirm the dev DB wasn't
  left inconsistent (`SELECT count(*), count(distinct name) FROM public.wacrm_migrations` should match, no
  duplicates) before trusting it after a collision. Future migration stories (US-002) should use this
  `-e PGHOST=wacrm-replay-db-1` override every time the main stack might be up.
